# 每日语音日记整理

将用户分散在一天的语音和文字碎片，整理为一篇忠实保存原话的个人日记，存入 IMA Note。

## ⚠️ 铁律：保留原文压倒一切

```
保留原文 ＞ 真实性 ＞ 可回忆性 ＞ 清晰度 ＞ 文学性
```

**用户原话**：不加引号，直接写原句，原句出现在 Bullet Points 中。

**非用户的话**（AI分类标签、小结、观察等）：用 📌 标记，与原话一眼可区分。

**唯一允许的修改**（为什么只允许这些：改写会丢失说话时的语气、思维路径、情感状态，多年后回看日记看到的应该是当时自己说的话）：
- 去掉语音转文字的明显无意义语气词："嗯"、"呃"、"那个那个"
- 补全省略的主语使句子可读（上下文明确时不补也行）
- 断句：一段长语音拆成几个逻辑完整的句子
- 核实错别字：人名、术语、网络用语（如"曲曲"≠"蛐蛐"、"胜子"≠"圣子"）

**严格禁止**（为什么禁止：每一项都会让原话失真）：
- ❌ 口语变书面语
- ❌ 压缩句子
- ❌ 替换用词
- ❌ 重组语序
- ❌ 添加用户没说的修饰词
- ❌ 引号包裹用户原话

## 触发与记录模式

### 两种场景

**场景A：用户输出想法（说"记一下"等）**
→ 只回复"已记录"，不做任何整理、不创建笔记、不随时更改笔记。
→ 与其他问题区分——如果用户的核心意图不是记录当天生活，就不触发日记流程。

**场景B：自动检测 + 整理执行**
→ 每天用户首次对话时，检测是否需要整理前一天日记：
  - 当前时间已过06:00日界线？
  - 上一个生活日的日记尚未创建？
  - 两个条件都满足 → 自动执行完整日记整理流程
→ 不依赖定时任务，靠对话开场时检测触发。

### 为什么不在其他时间整理

用户可能在一天内多次输出碎片，如果每次都整理会打断思路、产生重复笔记。只在跨过日界线后统一汇总，确保日记是完整的、不碎片化的。

## 整理流程（5 步）

```
1. 确定时间范围 → 2. 检索用户记录 → 3. 整理日记内容 → 4. 创建或合并 Note → 5. 确认结果
```

### Step 1：确定时间范围

**日界线**：每天早上 06:00。为什么用06:00不用00:00——用户的生活日从早起开始，凌晨几点还属于"昨天"的生活。

计算规则：
- 整理范围 = 上一个生活日 06:00 起，到当前生活日 05:59 止
- 日记日期标记 = 上一个生活日的日期
- 星期 = 上一个生活日是星期几

示例：
- 7月18日06:00执行 → 汇总7月17日06:00至7月18日05:59 → 日记标记**7月17日**
- 7月18日14:30执行 → 同上
- 7月18日03:00执行 → 汇总7月16日06:00至7月17日05:59 → 日记标记**7月16日**

### Step 2：检索用户记录

使用 `memory_recall` 检索指定时间范围内的对话记录：
1. `memory_recall(action="load", scope="daily_md", date_start="<上一个生活日>", date_end="<当前生活日>")` 获取日级摘要
2. `memory_recall(action="search", scope="qa", query="<上一个生活日的关键事件>")` 搜索完整对话细节
3. 如有 qa_session_id，用 `memory_recall(action="load", scope="qa", qa_session_id="<session_id>")` 获取完整原文

**内容过滤**（严格执行——日记只记录用户自己的声音，混入其他内容会破坏真实性）：

只保留用户本人发送的内容。必须剔除：
- ❌ 更早日期的记录（超出时间范围）
- ❌ AI 此前生成的总结和建议
- ❌ AI 的回复内容
- ❌ 课程原文、外部搜索内容
- ❌ 未经用户表达的推断
- ❌ 规则设定类对话（用户在更新日记流程规则时说的话，不属于生活记录）

**回忆往事**：如果用户在记录中回忆了过去的事，可以写入当天日记，但必须标注"当天回忆起的往事"，不误认为往事发生在当天。

### Step 3：整理日记内容

读取 `references/diary-structure.md` 获取完整的日记结构模板、各小节详细说明、写作风格规范。

**整理 ≠ 改写**。整理的过程是：
1. 把用户原句按主题归类到对应小节
2. 每个类别内部用 Bullet Points 列出用户原句（不加引号）
3. 非用户的话用 📌 标记
4. 核实语音转文字错别字（人名/术语/网络用语）

**标题格式**：

```
YYYY.MM.DD｜周X｜日记 ～事项1 ～事项2 ～事项3
```

3个事项从当日内容中提取，选择最开心/最有生命力/最浓墨重彩的事件、感受或发现。

示例：`2026.07.16｜周四｜日记 ～门框的新朋友 ～有了新的ai认知 ～做了个知识产品`

### Step 3.5：生成 Obsidian frontmatter 与实体链接（全部属性由 IMA 填写）

日记最终要进入用户的 Obsidian 知识系统，所以**整理完正文后，在整篇最顶部加一段 YAML frontmatter**。它让笔记能被 Dataview 检索、属性面板显示、图谱与反向链接连接。

完整模板、字段判断规则、实体链接规则见 `references/diary-structure.md` 的「Obsidian frontmatter 规范」小节。核心要点：

1. **所有属性都由 IMA 在整理时根据当天内容自行判断并填写**（occasion / focus / topics / highlights / people / knowledge_work / energy / location / related_project），不要把判断留给用户去补。正文原话一字不动。
2. **`occasion` 多选**：`daily`（默认）/ `work` / `special occasion` / `letter` / `personal reflection` / `monthly` / `weekly`，一篇可挂多个。文件夹已按大类分，occasion 是更细的标签，IMA 日记全进 `01 Daily`。
3. **`focus` 关联八个人生课题**：用 `[[八个人生课题#<课题名>]]` 链到「03 八个人生课题」对应章节（如 `[[八个人生课题#🌻自我]]`），当天触及哪个链哪个，可多选可留空。
4. **`topics` 与 `highlights` 分开**：标题 `～` 里偏主题/人事的进 `topics`，偏情绪/生命力（开心的事、有生命力的事）的进 `highlights`。`～` 不一定是主题，逐个判断归属。
5. **`knowledge_work` 关联知识工作库**：当天涉及的知识工作 / 项目笔记，用 `[[04_KNOWLEDGE WORK/名称]]` 指向对应笔记（注意文件夹名带下划线）；相关项目主页用 `related_project: [[项目名]]`。
6. **`[[链接]]` 只放进 frontmatter 的 `people / knowledge_work / related_project / focus`，正文原话一字不动**——Obsidian 会解析 frontmatter 里的 `[[ ]]` 成真实链接，既进图谱又不违背「保留原文」铁律。

**⚠️ 导出契约（与 Mac 导出脚本对齐）**：IMA 笔记以 Markdown 存储，正文要有真实的段落 / 标题 / 项目符号换行。导出脚本用 `get_doc_content(target_content_format=1)` 取 Markdown，会原样保留这些分段。**严禁把整篇压成无换行的纯文本**（`format=0` 会丢光换行，日记不可读，已踩坑）——正文分段质量直接决定 Obsidian 里的可读性。

### Step 4：创建或合并 Note


#### 检查是否已存在同日日记

1. `search_note` 用标题关键词搜索（如搜索"07.16｜日记"）
2. 找到标题完全匹配 → 合并流程
3. 没找到 → 新建流程

#### 新建流程

1. 组装完整的日记 Markdown 内容：**顺序为「最顶部 Obsidian frontmatter（见 Step 3.5）→ 标题 → 正文开头元信息 → 各正文小节」**
2. 内容较长时走 COS 上传路径：`file_write` 写 `.md` 文件 → `ima_cos_util -f <文件路径>` 上传获取 cosKey → `push_note` 用 `content_cos_key` 写入
3. 内容较短时可直接 `import_doc` 创建

#### 合并流程

1. 从 `search_note` 获取已有笔记的 `note_id`
2. `export_note` 读取已有笔记内容
3. 比对找出尚未收录的新记录
4. `export_note_blocks` 获取 block 结构
5. `update_note` 在对应位置追加新内容或替换旧内容
6. 追加内容包括：遗漏的记录 + "最后更新时间"标注

**不要重复创建第二篇同日日记**。为什么——用户可能一天内多次说"记一下"，每次都应该把新内容合并到同一天的日记里。

### Step 5：确认结果

向用户报告：
- ✅ 日记已创建 / 已合并更新
- 📅 日记归属日期
- 📊 原始记录数量
- ⏰ 第一条 / 最后一条记录时间
- 📝 日记标题
- 🔄 如有合并：新增了哪些内容

如果时间范围内没有任何用户记录：
- ❌ 不创建空白日记
- 📋 只报告："上一生活日没有收到日记素材"

## 异常情况

| 情况 | 处理 | 为什么这样处理 |
|------|------|---------------|
| 无记录 | 不创建空白日记 | 空白日记没有意义，多年后翻到会困惑 |
| 只有一条极短记录 | 可创建简短日记，不扩写 | 扩写会伪装成充实的一天，失真 |
| 记录存在矛盾 | 保留矛盾，写"早些时候我觉得……后来我又觉得……" | 不替用户选择哪个才是真实想法 |
| 高度私密内容 | 忠实保存，不自动引用或改写 | 隐私边界由用户自己决定 |
| 笔记API失败 | 查看错误码：210009内容过大→拆分；210005权限不足→告知用户 | 技术问题需要技术方案 |

## 正确做法 vs 错误做法（示例）

| 用户原话 | ✅ 正确（保留原文，不加引号） | ❌ 错误（改写） |
|---------|-------------------|------------------|
| 今天很惊喜地发现车改了，比我的预想的进度要快 | 今天很惊喜地发现车改了，比我的预想的进度要快 | 车改装进度比预想快 |
| 可能我之后再做一个滑轨，然后再买个冰箱，就能都后面就已经好了 | 可能之后再做一个滑轨，再买个冰箱，后面就都好了 | 接下来计划做个滑轨，再买个小冰箱 |
| 我执着的不是这个人，而是结果 | 我执着的不是这个人，而是结果 | 原来我执着的是结果而非人 |

## 工作流示例

### 示例1：用户说"记一下今天的事"

```
用户: "记一下，今天门框交了一个好朋友"
AI: "已记录。"  ← 只记录，不整理
```

### 示例2：自动检测触发整理

```
AI 检测: 当前时间 7月18日14:30，已过06:00日界线，7月17日日记未创建
→ 自动执行整理流程
→ Step 1: 整理范围 = 7月17日06:00至7月18日05:59
→ Step 2: 检索该时间范围内所有用户记录
→ Step 3: 整理日记内容（原句分类，不加引号，非原话用📌标记）
→ Step 4: search_note 检查是否已有7月17日日记 → 无 → 新建
→ Step 5: 报告结果
```

### 示例3：合并已有日记

```
AI 检测: 7月17日日记已存在
→ Step 4: search_note 找到已有笔记 → 进入合并流程
→ 比对发现新增了下午的一条记录
→ update_note 追加新内容，标注"最后更新时间：7月18日14:30"
→ Step 5: 报告合并结果
```
