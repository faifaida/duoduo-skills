# duoduo-weekly-review-calendar（周复盘 → 周报 → 下周日历）

多多个人 Life OS 的每周仪式。参考 `email-to-calendar`（先提取→提问→**用户确认后才写日历**）和
`weekly-life-os-calendar`（六维周计划 + 月相 + CalDAV 写入）两个技能融合而成，新增：**每周一 13:00
自动触发**、**日记周报格式产出**、**上周 calendar 完成情况核对 + 未完成标灰**。

> 核心哲学（来自 `02_CONTEXT/08 多多生活系统.md`）：**Follow Earth. Not Calendar.**
> 不可移动现实责任 → 季节/浪季/地点 → 身体与项目 → 月相/节气象征节奏。
> **不要把每一天排满——保留弹性和偶然性。**

## 何时触发
- **自动**：每周一 13:00（对应自动化）。
- **手动**：多多说「周复盘 / 周报 / 下周计划 / 和下周对齐」等。
- 时间窗口：
  - **复盘窗口** = 上周一 → 上周日（刚结束的完整一周）。若手动在周中跑，则复盘「上周一 → 今天」。
  - **规划窗口** = 本周今天（周一）→ 本周日。

## ⚠️ 铁律（对齐 email-to-calendar 的"先确认后写"）
1. **写日历前必须先把下周计划草稿 + 待对齐问题给多多，等她回复**。绝不在她确认前擅自写/改/删任何事件。
2. **只用她已有的日历与颜色**（见下方标签表），绝不新建日历、不发明颜色。
3. **日记里能回答的问题自己答**（从日记提炼），**答不出的列出来问她**，不硬编。
4. **不要把每天排满**——每天留 1–2h 弹性，保留偶然性。
5. 不修改 `02_CONTEXT` 任何核心文件。未授权前不对外发布/发送/付款。

## 输入文件（相对 Vault 根）
1. `07_Journals/01 Daily/<YYYY>/`（2026-08-03 起按年归档，遍历对应年份子目录如 `01 Daily/2026/`）—— 读复盘窗口内的日记（文件名形如 `2026.07.20｜周一｜日记 ～…`）。
   提炼：最有生命力/最耗能时刻、反复主题、未完成任务、身体/情绪/睡眠信号、四方向进展；**并额外沉淀两节：「本周 4 个可复用方法 / SOP」与「本周内容选题」（供月度复盘复用，详见下方周报格式）**。
2. `02_CONTEXT/08 多多生活系统.md` —— Life OS 权威文件（北极星 Alive、四季、月相四段、节气、复盘五问）。**每周必读并融汇。**
3. `07_Journals/03 Journal reviews/<YYYY-MM>/` —— 上一份 `周计划_YYYY-MM-DD_节奏.md`（2026-08-03 起按月归档在 `03 Journal reviews/<YYYY-MM>/` 子目录），用来**核对上周排进日历的任务清单**。
4. `03_ACTIVE PROJECTS/ai个人公司/公司档案/` —— 公司侧不可移动事项（知识库上架、青旅节点等），避免与个人日历冲突。

## 月相定位（每周先做）
- 月相四段（每段约 7–8 天，滚动、不从周一切；按多多 2026-07-22 批复统一）：
  - 🌑 新月→上弦 = **启动期** · 对外说法：支线任务 · 创意表达支线 / 个人提升 / 生活方式（创意表达 / 学习 / 开始实验 / 建立新结构）
  - 🌓 上弦→满月 = **推进期** · 对外说法：支线任务 · 身体 / 自我 / 美丽（身体能量 / 重复练习 / 解决阻力 / 深度建设）
  - 🌕 满月→下弦 = **爆发 · 释放期** · 对外说法：支线任务 · 生活项目 / 探索 / 关系（完成 / 发布 / 展示 / 活动 / 销售反馈）
  - 🌗 下弦→新月 = **收尾 · 内观期** · 对外说法：主线任务 · 青旅 / 事业主线 / 职业 / 资源 / 个人公司（整理 / 复盘 / 减少扩张 / 修复休息）
- 不代表月相客观导致能量，只是多多采用的行为提示；现实截止日期、合同、现金流优先。
- 拿当前月相：`WebSearch「YYYY MM moon phases」`，判断本周落在哪一段，据此建议本周适合/不适合推进什么。
- 2026 锚点：新月 7/14、上弦 7/21、满月 7/29、**下弦 8/6**、下一新月 8/13。🔑 周级定调（2026-08-03 多多）：含满月尾巴的那一周 = 🌕 爆发/释放（生活项目）；其下一周 = 🌗 收尾/内观（事业主线 / 决策清障）。

## 流程（7 步）

### Step 1 — 定位月相 + 读 Life OS
拿本周月相段（WebSearch），读 `02_CONTEXT/08 多多生活系统.md`，确定本周节奏基调。

### Step 2 — 读上周日记，写「日记周报」
从 `07_Journals/01 Daily/<YYYY>/`（2026-08-03 起按年归档，遍历对应年份子目录）读复盘窗口全部日记，按多多的口吻提炼（保留她的原声、不美化、不鸡汤）。

### Step 3 — 用日记回答固定六问（答不出的标「待多多确认」）
这组问题是多多定的，**日记里能答的自己答，答不出/拿不准的列出来问她**：
1. **这周最有生命力 & 最耗能的时刻**（来自日记）
2. **下周不可移动的工作与生活安排**（硬日程）
3. **当前身体 / 情绪 / 睡眠状态**（从日记推断，标「需你确认真实状态」）
4. **下周四方向分别想推进什么**：① 青旅/工作主线 ② 身体与能量 ③ 创意变现 ④ 大生活项目
5. **最重要的一件事 + 最想避免的陷阱**
6. **下周节奏偏好**：冲刺 / 恢复 / 探索 / 整合
外加：**可以做 / 不要做**清单、**一个让生活变得有趣的行动**、**周末复盘问题**
（周末复盘问题须含 Life OS 月相五问：本阶段唯一主要结果完成了吗？什么让我更 Alive？什么在消耗我？四项中哪项被挤压？下阶段要停止什么？）

### Step 4 — 核对上周 calendar 完成情况 + 未完成标灰
1. 读上一份 `周计划_*.md` 里排进日历的任务清单；用 CalDAV 读上周实际事件：
   `python caldav_tool.py events --calendar <名> --from <上周一> --to <上周日>`（逐个相关日历）。
2. **和多多确认每项完成情况**（她拍板哪些没做）。
3. **未完成的标灰**：⚠️ 原生 Apple Calendar **不能给单个事件单独改色**（颜色跟日历走）。所以"标灰"需先定机制，
   **首次跑本技能前必须向多多确认用哪种**（见「标灰机制」小节），确认后固定下来。

### Step 5 — 产出六维下周计划草稿（多多的周报格式），呈现并等回复
按下方「周报格式」写草稿，把 Step 3 里"待多多确认"的问题一并列在「待你核对」区，
**呈现给多多 → STOP，等她回复**。不要在她回复前写日历。

### Step 6 — 她回复后，写进 iCloud 日历
- 用 `duoduo-caldav-calendar-write` 规则写事件；**只用她已有日历 + 现有颜色**。
- 冲突处理：**同色可直接放；不同色/占位冲突先判断能判断的，判断不清就问她，绝不硬放**
  （例：全天外出 100km 与当天健身 → 当天不排健身、挪到相邻空闲日）。
- 无明确时间的事项 → **默认 1 小时块**（对齐 caldav 技能规则）。
- 时间块惯例（多多 2026-07-24 确立）：工作类→15:00–20:00；个人照护/家务类→13:00–15:00 或 20:00–22:00；
  其余（运动/探索/社交/家人/活动/会议/提升）→沿用日记具体时间，无时间则默认块。

### Step 7 — 落盘
写 `07_Journals/03 Journal reviews/<YYYY-MM>/周计划_YYYY-MM-DD_节奏.md`（2026-08-03 起按月归档在 `03 Journal reviews/<YYYY-MM>/` 子目录），frontmatter 含 week / rhythm / moon / source / status。

> ⚠️ **命名铁律（2026-08-02 踩坑后固化）**：`YYYY-MM-DD` 一律用**被规划周的周一**（不是被复盘周的周一）。
> 已有链条：`周计划_2026-07-27_爆发.md`（覆盖 07-27→08-02）→ `周计划_2026-08-03_爆发释放.md`（覆盖 08-03→08-09，节律 = 🌕 满月→下弦 爆发/释放）。
> 自动化 prompt 里若写「用 run_date-6 命名」，**不要照做**——那会覆盖上一周的计划文档，而它正是标灰核对的唯一依据。
> 落盘前先 `ls` 确认目标文件名不存在；若存在，改用规划周命名并在 frontmatter 加 `命名说明` 字段。

### Step 4 补充 — 完成度判定必须三方交叉（2026-08-02 固化）
多多会**大量手动改日历**（挪时段、删事件、自加新事项），所以「事件还在日历上」≠ 完成，「事件不在了」≠ 没做。
判定必须交叉三个源：
1. **日历读回**：`wb-` 前缀 = agent 写入的；无前缀 = 她手动加的。事件被挪时段/被删都只是信号，不是结论。
2. **日记**（`07_Journals/01 Daily/<YYYY>/`，2026-08-03 起按年归档，遍历对应年份子目录）：唯一能证明"做了"的直接证据。
3. **公司档案**（`03_ACTIVE PROJECTS/ai个人公司/公司档案/01_总经办/次日任务计划_*.md`、`06_待多多审核/`）：
   公司侧产出与阻塞项能反证工作类计划项推没推动（例：「视频已发布」可被 06 待审里仍挂着的成片直接证伪）。
   顺带产出高价值信号：**积压在多多身上的决定项清单**——这类瓶颈应写进周报「最重要一件事」。

**可判定 ❌ 未完成（可标灰）的硬证据**，满足其一即可：
- 多多本人在后续日期**重排了同一件事**（最硬。例：7/27「搞定手机号」→ 她 7/28、7/30 两次重排「移动办卡」）。
- 日记明确写了没做 / 被取消。

**其余一律列「待定」，不动日历**，在周报「待你核对」区逐条问她。宁可少标，不可错标。
计划项若已被她从日历删除 → 事件不存在，**无法标灰**，只在文档记录「已从日历移除」并问是放弃还是顺延。

## 标灰机制（首次跑前必须和多多确认）
原生 Apple Calendar 单事件不能独立改色。可选：
- **A. 专门建一个「未完成」灰色日历**，把上周未完成事件**移**过去（会改变事件所属日历——多多此前说过尽量别改类别，需她同意）。
- **B. 标题前缀标记**：给未完成事件标题前加 `⬜️未完成 `（不改颜色，但一眼可见；最轻量）。
- **C. Fantastical** 等支持单事件着色的客户端。
- CalDAV 的 `COLOR` 属性 Apple Calendar 基本不渲染，别指望它。
> ✅ **已定（多多 2026-07-27 首次确认）= 方案 A**：灰色「未完成」日历已用 CalDAV MKCALENDAR 建好
> （`/1501357648/calendars/0BF8B341-282F-426D-9F62-2501A96FBF30/`，颜色 #8E8E93）。
> 标灰操作 = `add` 复制事件进「未完成」（notes 注明原日历）→ `delete-match` 删原件。以后每周直接执行，不再询问。
> 注意：2026-07-22 那次「日历不标灰、只在文档记 ❌」是当周口头决定，已被本机制覆盖。

## CalDAV 写入（永久免权限）
- 工具：`~/.workbuddy/caldav/caldav_tool.py`，venv python `/Users/Zhuanz/.workbuddy/binaries/python/envs/default/bin/python`。
- 任何命令前 `unset HTTP_PROXY HTTPS_PROXY http_proxy https_proxy`。
- 命令：`list` / `events --calendar <名> [--from --to]` / `add --calendar <名> --title --start --end [--notes]` /
  `delete-match --calendar <名> --contains <文本> [--from --to]`。
- 改时间 = 删旧 + 加新（无 update 命令）；删用标题精确匹配 + 日期守卫防误删。
- ⚠️ 弃用 osascript/EventKit（本环境走不通）；只用 CalDAV。
- 🔴 **实测复核铁律（2026-08-03 踩坑·已二次修正）**：
  1. `add` 返回的 `VERIFY: OK` **只代表 HTTP 201，不代表事件真的落盘**——必须读回核对。
  2. **`events --from/--to` 查询会漏掉范围最末一天**（时区/截止处理 bug）。用 `--from <周一首> --to <周日>` 读回时，**周日事件全部看不到**，会误判「被丢弃」→ 进而后台重试 → 堆出大量重复事件（2026-08-03 实测：误判周日 8/9 丢失，重试后造出 26 条重复 + 2 探针 + 多个改名变体，事后全量去重才救回）。**正确读回方式二选一**：① `--to` 设到**下周一**（如周日是 8/9，则 `--to 2026-08-10`），把末日包进去；② 不加 `--from/--to` 直接 `events --calendar <名>` 列出全部，再 `grep` 关键词/日期。**绝不可用 `--to` 等于周日当天的 inclusive 写法当复核手段。**
  3. 发现「缺失」先怀疑是查询 bug，再用「无过滤读回」确认真实落盘状态；**确认真的缺失才重试，且重试前先查是否已有重复**（避免越补越多）。iCloud 真实节流极少见，绝大多数「看不到」都是这个查询 bug。
