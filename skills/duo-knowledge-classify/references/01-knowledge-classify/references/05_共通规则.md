## 2. Properties 规则（只增不改名）

**通用字段**
```yaml
title:
collected_date:
author:
url:
source:            # xiaohongshu / weread / gdrive / ...
category:
status:            # captured / processed / promoted / archived / broken-source
focus:             # 人生课题，纯文本列表
why_saved:         # ⚠️ 多多自己的字段，AI 永远留空
ai_inference:      # ⚠️ AI 推断只能写这里
company_threads:
action:
related:
knowledge_work:    # 升级后填指向 T10 的 wikilink 字符串
```

**平台专属**
- 小红书：`type: xhs-save`、`source: xiaohongshu`、`rights: external-source`；专辑索引页 `type: xhs-board`
- 微信读书：`type: weread-highlight`、`source: weread`、`rights: quote-with-attribution`，可增 `book / chapter / highlight_count`

**可选增补**：`media_type / published_date / credibility / rights / batch / life_topics / project / content_potential / product_potential`

### why_saved vs ai_inference（关键分流）
2026-07-29 发现小红书 1158/1166 条的 `why_saved` 是 `"[AI推断]…"`（旧自动化替填的）。
处理方式：`[AI推断]` 那段移到 `ai_inference`，`why_saved` **留空给多多填**。
**红线：绝不把 AI 推断写进 `why_saved`。**

### frontmatter 语法铁律
属性值里**禁止裸 `[[ ]]`** —— YAML 会把它当嵌套列表，整块 frontmatter 解析失败，Obsidian 所有属性都不显示。
wikilink 只放正文；`knowledge_work` 这种必须写 wikilink 的，用引号包成字符串。

## 6. 交差前自检（多多明确要求，误报成功比不交更糟）

- **数量核对**：源计数 vs 落盘计数，差额必须能解释清楚。
- **抽查 3–5 篇**：frontmatter 完整、正文非空、无 YAML 解析错。
- **状态文件**：去重表 / 索引是否同步更新。
- **能实测就实测**，不许断言「应该好了」。
- 跨文件引用一致性（wikilink 指向的目标真实存在）。

## 7. 回报规范

- 当天**只有一份** `03_资料员/回报_YYYYMMDD.md`，多阶段/多放行项**全部追加进同一份**。
- 🚫 不存在 `回报_YYYYMMDD_主题.md`、`回报_巡检XX点.md` 等变体。
- 纯执行类任务**不写方案文件**；只有明确要求「先出方案」时才写一份，命名如 `icloud_整理方案_YYYYMMDD.md`。
- 文风：极简口语、短 bullet、动作导向，一眼扫完能拍板。

## 10. 双层归位模板规范（Topic Map vs Research）

大外部源整理（D 通道）走 SKILL.md「二-B 双层归位」，两套 frontmatter 不能混、不能套 T04：

**Topic Map（`02_TOPIC_MAPS/`，`type: topic-map`）** —— 资产 / 分类索引层
```yaml
type: topic-map
map_type: <资产类型，如 digital-asset-inventory>
status: developing
corresponds_to: <主 R 研究名，如 R5_品牌与营销>
related: ["R3_...", "R4_...", ...]   # 指向所有相关 R
source: <来源与实测时间>
created: YYYY-MM-DD
last_updated: YYYY-MM-DD
note: 一句话定位
```
正文：MOC 结构树 + 分类索引（总览表 + 各分类明细）+ 清理 / 去重结果 + 操作注意事项 + 整理统计 + 待核对事项。

**Research 补充 / 新建（`03 Research/`，`type: knowledge-note`）** —— 消化后方法论 / 生活主题层
```yaml
type: knowledge-note
status: to-review
source: <来源，关联对应 T>
ai_inferred: true|false
related: ["T17_...", "R5_..."]
created: YYYY-MM-DD
note: 一句话说明
```
正文：MOC + 分节（按主题）+ 提取内容，事实 / 理解 / 推断分别标 `[原始事实]` / `[你的理解]` / `[AI推断]`，回溯到具体来源日期 / 文件。

**❌ 禁止**：用 `08_TEMPLATES/T04_每周复盘.md`（月相 / 周计划九节）写 topic map 或 research。早期百度云整理曾错套 T04，已纠正。

## 11. 同步铁律（research ↔ topic map 必须双向同步，2026-08-09 新增）

- **规则**：每在 `03 Research` 新增 / 补一篇笔记（无论新建 R 还是补进已有 R），**必须同步**在对应（或新建）的 `02_TOPIC_MAPS` 主题地图里：
  1. 加该笔记的索引条目（wikilink + 一句话说明 + `source` 标注来源，如 `gdrive:` / 百度网盘 MCP / weread）；
  2. 若该 R 尚无对应 topic map，先建 `Txx_…知识地图`（`type: topic-map`、`corresponds_to` 指向该 R、填补空缺编号），再补索引。
- **反向**：topic map 里新增一个来源资产，若它值得消化成方法论，必须补进对应 R 笔记，不能只留在 map。
- **为什么**：早期云盘整理曾出现「笔记建了但 topic map 没索引 / R 缺 T 无法索引」的脱节，导致资产地图与研究方法论两张皮。此铁律防再犯。
- 适用范围：大外部源整理（D 通道「双层归位」）、日常 sources 升级均适用。
