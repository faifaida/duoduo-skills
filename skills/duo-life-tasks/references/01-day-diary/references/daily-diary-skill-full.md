# 每日语音日记整理

将用户分散在一天的语音和文字碎片，整理为一篇忠实保存原话的个人日记，存入 IMA Note。

## ⚠️ 铁律：保留原文压倒一切

```
保留原文 ＞ 真实性 ＞ 可回忆性 ＞ 清晰度 ＞ 文学性
```

**用户原话**：不加引号，直接写原句，原句出现在 Bullet Points 中。

**非用户的话**（AI分类标签、小结、观察等）：用 📌 标记，与原话一眼可区分。

**唯一允许的修改**（为什么只允许这些：改写会丢失说话时的语气、思维路径、情感状态，多年后回看日记看到的应该是当时自己说的话）：
- 去掉语音转文字的明显无意义语气词："嗯"、"呃"、"那个那个"
- 补全省略的主语使句子可读（上下文明确时不补也行）
- 断句：一段长语音拆成几个逻辑完整的句子
- 核实错别字：人名、术语、网络用语（如"曲曲"≠"蛐蛐"、"胜子"≠"圣子"）

**严格禁止**（为什么禁止：每一项都会让原话失真）：
- ❌ 口语变书面语
- ❌ 压缩句子
- ❌ 替换用词
- ❌ 重组语序
- ❌ 添加用户没说的修饰词
- ❌ 引号包裹用户原话

## 触发与记录模式

### 两种场景

**场景A：用户输出想法（说"记一下"等）**
→ 只回复"已记录"三个字。**不总结、不解释、不引用、不做任何其他操作。**（用户明确：没到封笔记时不要给总结，就回三字，不需要思考）
→ 不做任何整理、不创建笔记、不随时更改笔记、**不写入记忆（memory_md）**、不做任何其他操作。
→ 当日的碎片化记录随对话自然留存于 qa 层，下次跨过 06:00 日界线时由场景B自动检测流程统一检索、整理。
→ 与其他问题区分——如果用户的核心意图不是记录当天生活，就不触发日记流程。

**场景B：自动检测 + 整理执行**
→ **触发时机（满足任一即触发）**：
  1. **跨 06:00 自动触发**：跨过 06:00 日界线后的**第一条用户消息**即触发检测——无论是否新开对话、是否带"记一下"、消息内容是日记碎片还是普通提问。
     - 当前时间已过 06:00 日界线？
     - 上一个生活日的日记尚未创建？
     - 两个条件都满足 → 自动执行完整日记整理流程
  2. **手动封笔记触发**：用户在当天生活日内（06:00 之后、次日 06:00 之前）提及"**封口**"或"**封笔记**"时，立即整理**当天生活日**的日记（而非等到次日跨 06:00）。
     - 封笔记 = 用户主动宣布今天记录结束、现在就整理
     - 整理范围 = 当天生活日 06:00 至当前时间
     - 整理完回复确认结果；后续若还有新碎片，按场景A正常记录，次日 06:00 后如检测到日记已存在则走合并流程
→ 检测并（如需）整理完毕后，再正常处理本条消息本身：若它是日记碎片，按场景A回"已记录"；若它是提问，正常回答。
→ 不依赖定时任务，靠"跨过日界线后的首条消息"或"手动封笔记"检测触发。
→ ⚠️ 连续对话跨天也适用：即使同一场对话从昨天延续到今天，只要时间跨过 06:00 且当天首条消息到来，就触发对"昨天"的整理。

### 为什么不在其他时间整理

用户可能在一天内多次输出碎片，如果每次都整理会打断思路、产生重复笔记。只在跨过日界线后统一汇总，确保日记是完整的、不碎片化的。

## 整理流程（5 步）

```
1. 确定时间范围 → 2. 检索用户记录 → 3. 整理日记内容 → 3.5 生成 Obsidian frontmatter → 4. 创建或合并 Note → 5. 确认结果
```

### Step 1：确定时间范围

**日界线**：每天早上 06:00。为什么用06:00不用00:00——用户的生活日从早起开始，凌晨几点还属于"昨天"的生活。

计算规则：
- 整理范围 = 上一个生活日 06:00 起，到当前生活日 05:59 止
- 日记日期标记 = 上一个生活日的日期
- 星期 = 上一个生活日是星期几

示例：
- 7月18日06:00执行 → 汇总7月17日06:00至7月18日05:59 → 日记标记**7月17日**
- 7月18日14:30执行 → 同上
- 7月18日03:00执行 → 汇总7月16日06:00至7月17日05:59 → 日记标记**7月16日**

### Step 2：检索用户记录

使用 `memory_recall` 检索指定时间范围内的对话记录：
1. `memory_recall(action="load", scope="daily_md", date_start="<上一个生活日>", date_end="<当前生活日>")` 获取日级摘要
2. `memory_recall(action="search", scope="qa", query="<上一个生活日的关键事件>")` 搜索完整对话细节
3. 如有 qa_session_id，用 `memory_recall(action="load", scope="qa", qa_session_id="<session_id>")` 获取完整原文

**内容过滤**（严格执行——日记只记录用户自己的声音，混入其他内容会破坏真实性）：

只保留用户本人发送的内容。必须剔除：
- ❌ 更早日期的记录（超出时间范围）
- ❌ AI 此前生成的总结和建议
- ❌ AI 的回复内容
- ❌ 课程原文、外部搜索内容
- ❌ 未经用户表达的推断
- ❌ 规则设定类对话（用户在更新日记流程规则时说的话，不属于生活记录）

**回忆往事**：如果用户在记录中回忆了过去的事，可以写入当天日记，但必须标注"当天回忆起的往事"，不误认为往事发生在当天。

### Step 3：整理日记内容

读取 `references/diary-structure.md` 获取完整的日记结构模板、各小节详细说明、写作风格规范。

**整理 ≠ 改写**。整理的过程是：
1. 把用户原句按主题归类到对应小节
2. 每个类别内部用 Bullet Points 列出用户原句（不加引号）
3. 非用户的话用 📌 标记
4. 核实语音转文字错别字（人名/术语/网络用语）
5. **合并同一件事的分段语音**：每条语音限 60 秒，用户常把同一件事分成多条消息连续发。整理时若多条连续碎片明显在讲同一件事 / 同一个想法 / 同一个事件，应**合并为一条连贯的原话记录**，不要按消息条数拆成多条独立 bullet。判断依据：话题连续、时间紧邻、语义承接（上一条没说完下一条接着说）。合并时仍只做断句和去语气词，不替用户补全逻辑、不改写。
6. **保留想法 / 灵感 / 认知的触发背景**：用户的新认知、判断、灵感很多不是凭空产生的，而是由当天某个具体事件、对话、经历、阅读或观看内容"戳中"才冒出来的。整理到「我想到的事情」「灵感与创造」小节时，若某条明显由某件事触发，**必须在该条目前用一句话交代触发它的事件或背景（context）**，不要只留结论。触发背景从「今日发生」或当天碎片里能找到对应就写上；由更早往事触发的，按"当天回忆起的往事"规则标注。否则孤立的认知多年后回看会失去线索，看不懂当时在回应什么。

**标题格式**：

```
YYYY.MM.DD｜周X｜日记 ～事项1 ～事项2 ～事项3
```

3个事项从当日内容中提取，选择最开心/最有生命力/最浓墨重彩的事件、感受或发现。

示例：`2026.07.16｜周四｜日记 ～门框的新朋友 ～有了新的ai认知 ～做了个知识产品`

### Step 3.5：生成 Obsidian frontmatter 与实体链接（全部属性由 IMA 填写）

日记最终要进入用户的 Obsidian 知识系统，所以**整理完正文后，在整篇最顶部加一段 YAML frontmatter**。它让笔记能被 Dataview 检索、属性面板显示、图谱与反向链接连接。

完整模板、字段判断规则、实体链接规则见 `references/diary-structure.md` 的「Obsidian frontmatter 规范」小节。核心要点：

1. **所有属性都由 IMA 在整理时根据当天内容自行判断并填写**（occasion / focus / topics / highlights / people / knowledge_work / energy / location / related_project），不要把判断留给用户去补。正文原话一字不动。
2. **`occasion` 多选**：`daily`（默认）/ `work` / `special occasion` / `letter` / `personal reflection` / `monthly` / `weekly`，一篇可挂多个。文件夹已按大类分，occasion 是更细的标签，IMA 日记全进 `01 Daily`。
3. **`focus` 关联八个人生课题**：用 `[[八个人生课题#<课题名>]]` 链到「03 八个人生课题」对应章节（如 `[[八个人生课题#🌻自我]]`），当天触及哪个链哪个，可多选可留空。
4. **`topics` 与 `highlights` 分开**：标题 `～` 里偏主题/人事的进 `topics`，偏情绪/生命力（开心的事、有生命力的事）的进 `highlights`。`～` 不一定是主题，逐个判断归属。
5. **`knowledge_work` 关联知识工作库**：当天涉及的知识工作 / 项目笔记，用 `[[04_KNOWLEDGE WORK/名称]]` 指向对应笔记（注意文件夹名带下划线）；相关项目主页用 `related_project: [[项目名]]`。
6. **`[[链接]]` 只放进 frontmatter 的 `people / knowledge_work / related_project / focus`，正文原话一字不动**——Obsidian 会解析 frontmatter 里的 `[[ ]]` 成真实链接，既进图谱又不违背「保留原文」铁律。

**⚠️ 导出契约（与 Mac 导出脚本对齐）**：IMA 笔记以 Markdown 存储，正文要有真实的段落 / 标题 / 项目符号换行。导出脚本用 `get_doc_content(target_content_format=1)` 取 Markdown，会原样保留这些分段。**严禁把整篇压成无换行的纯文本**（`format=0` 会丢光换行，日记不可读，已踩坑）——正文分段质量直接决定 Obsidian 里的可读性。

### Step 4：创建或合并 Note

使用 IMA Note API（需先加载 `ima-note` 技能获取接口详情）。

#### 检查是否已存在同日日记

1. `search_note` 用标题关键词搜索（如搜索"07.16｜日记"）
2. 找到标题完全匹配 → 合并流程
3. 没找到 → 新建流程
4. ⚠️ **跨压缩/中断恢复后必须重新 `search_note`**：若上一轮对话被压缩截断，摘要里写的"待创建/待 push"可能已经在截断前实际执行过。恢复后**不要依赖摘要的"待执行"描述**，必须重新搜索确认当前真实状态，再决定是否 push——否则会重复创建同名日记（已发生 2026.07.31 重复两篇的事故）。

#### 新建流程

1. 组装完整的日记 Markdown 内容：**顺序为「最顶部 Obsidian frontmatter（见 Step 3.5）→ 标题 → 正文开头元信息 → 各正文小节」**
2. 内容较长时走 COS 上传路径：`file_write` 写 `.md` 文件 → `ima_cos_util -f <文件路径>` 上传获取 cosKey → `push_note` 用 `content_cos_key` 写入
3. 内容较短时可直接 `import_doc` 创建
4. **修正笔记标题（必做）**：因 frontmatter 在整篇最顶部，IMA 的标题自动提取会把首行 `type: journal` 误当成标题。创建成功后**必须调用 `rename_note`** 把标题改为正确的 H1 标题（即 `YYYY.MM.DD｜周X｜日记 ～事项1 ～事项2 ～事项3`），否则笔记在 IMA 里会显示成 "type: journal"。

#### 合并流程

1. 从 `search_note` 获取已有笔记的 `note_id`
2. `export_note` 读取已有笔记内容
3. 比对找出尚未收录的新记录
4. `export_note_blocks` 获取 block 结构
5. `update_note` 在对应位置追加新内容或替换旧内容
6. 追加内容包括：遗漏的记录 + "最后更新时间"标注

**不要重复创建第二篇同日日记**。为什么——用户可能一天内多次说"记一下"，每次都应该把新内容合并到同一天的日记里。

### Step 5：确认结果

向用户报告：
- ✅ 日记已创建 / 已合并更新
- 📅 日记归属日期
- 📊 原始记录数量
- ⏰ 第一条 / 最后一条记录时间
- 📝 日记标题
- 🔄 如有合并：新增了哪些内容

如果时间范围内没有任何用户记录：
- ❌ 不创建空白日记
- 📋 只报告："上一生活日没有收到日记素材"

## 异常情况

| 情况 | 处理 | 为什么这样处理 |
|------|------|---------------|
| 无记录 | 不创建空白日记 | 空白日记没有意义，多年后翻到会困惑 |
| 只有一条极短记录 | 可创建简短日记，不扩写 | 扩写会伪装成充实的一天，失真 |
| 记录存在矛盾 | 保留矛盾，写"早些时候我觉得……后来我又觉得……" | 不替用户选择哪个才是真实想法 |
| 高度私密内容 | 忠实保存，不自动引用或改写 | 隐私边界由用户自己决定 |
| 笔记API失败 | 查看错误码：210009内容过大→拆分；210005权限不足→告知用户 | 技术问题需要技术方案 |

## 正确做法 vs 错误做法（示例）

| 用户原话 | ✅ 正确（保留原文，不加引号） | ❌ 错误（改写） |
|---------|-------------------|------------------|
| 今天很惊喜地发现车改了，比我的预想的进度要快 | 今天很惊喜地发现车改了，比我的预想的进度要快 | 车改装进度比预想快 |
| 可能我之后再做一个滑轨，然后再买个冰箱，就能都后面就已经好了 | 可能之后再做一个滑轨，再买个冰箱，后面就都好了 | 接下来计划做个滑轨，再买个小冰箱 |
| 我执着的不是这个人，而是结果 | 我执着的不是这个人，而是结果 | 原来我执着的是结果而非人 |

# Part 2：references/diary-structure.md（日记正文结构模板）

# 日记正文结构模板

根据当天实际内容灵活使用以下结构。没有内容的部分可以省略，不要为了结构完整而虚构。

## Obsidian frontmatter 规范

放在整篇日记**最顶部**，用 `---` 包裹。这是让日记进入 Obsidian 知识系统的关键——有了它，笔记能被 Dataview 检索、属性面板显示、图谱与反向链接连接。

```yaml
---
type: journal
date: YYYY-MM-DD           # 日记归属日期，用连字符（与正文里点号格式不同，勿混）
weekday: 周X
occasion:                  # 多选：daily / work / special occasion / letter / personal reflection / monthly / weekly
  - daily
focus:                     # 关联八个人生课题（relation）：链到「03 八个人生课题」对应章节
  - "[[八个人生课题#🌻自我]]"
  - "[[八个人生课题#🦋探索]]"
topics:                    # 当天的「主题/人事/项目」——标题 ～ 里偏主题的事项
  - 事项（主题）
highlights:                # 当天的「情绪/生命力标记」——标题 ～ 里偏感受的事项（开心的事、有生命力的事…）
  - 有生命力的事
people:                    # 当天出现的人 / 宠物 / 博主，用 [[名称]]
  - "[[门框]]"
knowledge_work:            # 当天涉及的知识工作 / 项目笔记，用 [[04_KNOWLEDGE WORK/名称]]
  - "[[04_KNOWLEDGE WORK/XXX]]"
energy:                    # 可空：high / mid / low，或用户原话
location:                  # 可空
related_project:           # 可空，用 [[项目名]]
source: ima
---
```

### 字段判断规则（全部由 IMA 填写）

所有 frontmatter 属性都由 IMA 在整理时根据当天内容**自行判断并填写**，不要把判断留给用户去补（仅当某项确实无对应内容、且标注「可空」时留空）。正文原话一字不动——属性判断是 IMA 的归纳工作，不是用户的作业。

- **occasion**（多选，可多选可单值，必填至少一项）：当天日记的「类型标签」。全部选项：
  `daily`（普通生活日，默认）/ `work`（当天主要围绕工作·项目推进）/ `special occasion`（生日·节日·纪念日·旅行·重大 milestone·明显不寻常的一天）/ `letter`（信）/ `personal reflection`（个人反思）/ `monthly`（月度回顾）/ `weekly`（周回顾）。
  一篇日记可同时挂多个，例如某篇既是 `daily` 又逢 `special occasion`。
  ⚠️ 文件夹已按大类分（01 Daily / 02 Travel / 03 Reviews / 04 Reflections），occasion 是更细的标签，两者互补、不冲突。IMA 产出的日记一律进 `01 Daily`，occasion 标类型即可。
- **focus**（可空，多选，关联八个人生课题）：用 `[[八个人生课题#<课题名>]]` 链到「03 八个人生课题」对应章节。八个人生课题（名称一字不差，不可更改 / 合并 / 重命名）：
  `[[八个人生课题#🔥个人提升／技能]]`、`[[八个人生课题#🌻自我]]`、`[[八个人生课题#🍓关系]]`、`[[八个人生课题#🌍资源]]`、`[[八个人生课题#💫职业]]`、`[[八个人生课题#🦋探索]]`、`[[八个人生课题#💗美丽]]`、`[[八个人生课题#🍀生活方式／健康]]`。
  当天内容真正触及哪个就链哪个，没触及就不链；拿不准宁可留空，不硬凑。
- **topics**：标题 `～` 里**偏「主题 / 人事 / 项目」**的事项（例如「门框」「雀骨」「做了个知识产品」）。
- **highlights**（新字段）：标题 `～` 里**偏「情绪 / 生命力」**的事项（例如「来姨妈第一天」「今天最开心的事」「有生命力的事」）。
  👉 `～` 事项不一定是主题——有时是「今天让我开心的事 / 有生命力的事」。IMA 整理时**逐个判断**每个 `～` 事项归 topics 还是 highlights，不要无脑全塞 topics。
- **people**：当天出现的人 / 宠物 / 博主 → `[[名称]]`。
- **knowledge_work**：当天涉及的知识工作 / 项目笔记 → 用 `[[04_KNOWLEDGE WORK/名称]]` 指向对应笔记（注意文件夹名是 `04_KNOWLEDGE WORK`，下划线），自动与你的知识工作库关联。
- **related_project**（可空）：关联的项目主页 → `[[项目名]]`。

### 实体链接规范（重要）

**`[[链接]]` 只写进 frontmatter，正文原话一字不动。**

为什么——正文有「保留原文」铁律，往原句里塞 `[[ ]]` 就是改原文。而 Obsidian 会解析 frontmatter 里的 `[[ ]]` 成真实链接，一样进图谱和反向链接。所以链接放 frontmatter，正文保持用户原声，两全其美。

- frontmatter 里的 `[[ ]]` 必须用引号包裹（如 `"[[门框]]"`、`"[[04_KNOWLEDGE WORK/XXX]]"`），否则 YAML 解析报错。
- 拿不准是不是同一实体、或名字有歧义时，宁可少链接，不要瞎链。
- 同一实体在一天里多次出现，`people / knowledge_work / related_project` 里只写一次。

原始记录数量：X 条
第一条记录时间：HH:MM
最后一条记录时间：HH:MM

合并更新时追加：

最后更新时间：YYYY.MM.DD HH:MM

## 标题格式

```
YYYY.MM.DD｜周X｜日记 ～事项1 ～事项2 ～事项3
```

3个事项从当日内容中提取，选择最开心/最有生命力/最浓墨重彩的事件、感受或发现。**注意：`～` 后面跟的不全是「主题」——也可能是「今天让我开心的事 / 有生命力的事」这类情绪标记。整理时把这些情绪标记归入 frontmatter 的 `highlights`，主题归入 `topics`（见上方字段规则）。**

示例：`2026.07.16｜周四｜日记 ～门框的新朋友 ～有了新的ai认知 ～做了个知识产品`

## 正文结构

### 今日发生

按**时间块**组织当天发生的重要事情——用子标题把一天切分，每个时间块内再按事情逻辑列原句（不要纯按钟点流水账）：

#### 晨（醒来 — 约 10:00）
#### 上午（约 10:00 — 12:00）
#### 午后（约 12:00 — 17:00）
#### 傍晚（约 17:00 — 19:00）
#### 夜（19:00 以后）

每个时间块内用 Bullet Points 列出用户原句（去掉语气词后，不加引号）。保留：
- 人物、地点、行动
- 对话片段
- 决定
- 过程变化
- 有记忆价值的小细节

不要写成机械流水账——时间块内仍按事情的发展逻辑组织，不是按时间逐条罗列。
不要只剩下抽象概括——"今天出去了一趟"没有信息量，要保留具体的人和事。

### 当时的我

用 Bullet Points 列出用户当天提到的内在状态。保留用户原句的表述方式（不加引号）。

整理当天出现的主要：
- 情绪
- 身体感受
- 欲望
- 抗拒
- 兴奋
- 疲惫
- 矛盾
- 尚未得到答案的问题

区分瞬间情绪和持续状态。比如"当时突然一阵烦躁"和"整天都觉得闷"是两回事。
不要替用户诊断或分析。只记录状态，不解释原因、不判断性格、不贴标签。
非用户原话的总结性描述用📌标记。

### 我想到的事情

用 Bullet Points 列出用户当天提到的思维活动。保留用户原句的表述方式（不加引号）。

保留当天出现的：
- 新认知
- 联想
- 判断
- 疑问
- 价值观表达
- 对过去的重新理解
- 对未来的想象

清楚区分三类（用标签标注）：
- 💭 在考虑的可能性
- 📌 新认知 / 发现 / 判断（标注分类来源）
- ❓ 尚未确定的猜测

不要把正在思考的东西写成已确定的判断。

**保留触发源（重要）**：很多认知、判断、价值观表达不是凭空产生的，而是被当天某个具体事件、对话、经历、阅读或观看内容"戳中"才冒出来的。整理时如果某条想法明显由某件事触发，**必须在该条目前用一句话交代触发它的事件或背景（context）**，不要只把结论单独拎出来。格式示例：

- 触发：今天看孙林分享的夏威夷恋爱帖子，下面评论都在说"美好留在海岛、没法复刻" → 我突然释然了，原来很多人也害怕联系后事情会变，不是只有我
- 触发：前一阵看纪录片《亿万富翁的诞生》，讲互联网催化硅谷巨头 → 我现在觉得 2026 年的 AI 跟千禧年没有任何区别，是更大一波风口

为什么必须写——孤立的认知多年后回看会失去线索，看不懂当时在回应什么、为什么这么想。**触发背景从「今日发生」或当天碎片里能找到对应就写上；由更早的往事触发的，按"当天回忆起的往事"规则标注，不误认为发生在当天。**

### 灵感与创造

用 Bullet Points 列出用户当天提到的灵感。保留原始表达（不加引号），灵感最珍贵的就是发生时的原始形态。

记录：
- 内容选题
- 文案片段
- 产品想法
- 项目创意
- 审美灵感
- 想尝试的活动
- 值得保留的原话

**保留触发场景**：灵感也常是"看到什么 / 经历什么"之后冒出来的。如果某条灵感有明显的触发源（一个画面、一段话、一件事），在该条目前交代触发背景，不要只留结论——和「我想到的事情」小节的触发源规则一致。

### 工作与推进

用 Bullet Points 列出用户当天提到的工作事项。保留用户原句表述（不加引号），特别注意区分计划 vs 已完成。

记录当天涉及的：
- 项目进展
- 已完成事项
- 卡点
- 沟通情况
- 决策
- 等待他人的事情
- 下一步动作

不要把计划写成已经完成。如果用户说"我要去做XX"，记录的是"要去做XX"，不是"做了XX"。

### 明日与以后

只整理用户明确提到或能够直接从话语中识别的待办。分为三类：
- 明确要做：有具体意图的事情
- 等待别人：依赖他人推进的事项
- 📌 以后可能考虑：模糊想法，尚无行动计划

如果截止日期不明确，不要擅自设置日期。

### 今天留下来的几句话 ✨

选出 1 至 5 句最有生命力、最像用户、最值得多年后重新看到的原话。

尽量保留原句，只做必要的口语清理（去掉重复的语气词）。不加引号。
不要改写成更"优美"的句子。

### 今日小结

📌 用一小段自然的文字总结这一天。

要求：
- 80 至 180 字
- 不鸡汤
- 不强行积极
- 不使用空泛的"成长""疗愈""成为更好的自己"
- 写出这一天真正的主题、张力或变化
- 保持接近用户的语言风格

因为这是AI写的总结，所以用📌标记，与用户的原话区分开。

## AI观察（与日记正文分开）

📌 最后增加一个独立小节 AI观察，只写以下内容（如没有则忽略，每项控制在一至两句话）：

- 📌 今天最有生命力的瞬间
- 📌 今天最消耗我的事情
- 📌 今天反复出现的主题
- 📌 📌 一个值得以后观察但尚不能下结论的模式
- 📌 一个明天可以留意的问题

措辞必须审慎，使用：
- "可能……"
- "看起来……"
- "值得继续观察……"
- "仅根据今天的记录还不能确定……"

严禁：心理诊断、确定的人格判断、"你是一个XX类型的人"、给出确定性的结论。

因为全是AI推断，全部用📌标记。

## 写作风格规范

日记应该：
- 每个 Bullet Point 都是用户原句（去掉语气词后的原句，不加引号，不是改写版）
- 清楚但不僵硬
- 保留事件和情绪的复杂性
- 以 Bullet Points 为主，必要时穿插短段落
- 适度使用 emoji 烘托情绪和氛围——一段里 1-2 个即可，不要堆砌，不要用 emoji 替代文字或改变原文意思
- 避免大段 AI 散文
- 避免重复
- 避免过度美化
- 避免替用户制造人生意义
- 保留用户的幽默、矛盾和口语感
- 不把每一天都写成一次重大领悟

优先级排序：

保留原文 ＞ 真实性 ＞ 可回忆性 ＞ 清晰度 ＞ 文学性

标记系统：
- 用户原话：不加引号，直接写
- 📌 AI推断/总结/分类标签：一眼可区分
- 💭 用户正在考虑的可能性
- ❓ 尚未确定的猜测

不要用流畅的 AI 表达覆盖用户的原始想法。如果用户说的是"感觉有点烦"，不要改写成"今日心情略显低落"。

# 附录：踩坑记录与经验教训

1. **标题误提取**：frontmatter 在顶部时，IMA 把首行 `type: journal` 误当标题 → 必须在 Step 4 强制 `rename_note`。
2. **重复创建**：会话压缩后，摘要里写的"待创建/待 push"可能已实际执行过 → 恢复后必须重新 `search_note` 确认，不依赖摘要描述（2026.07.31 重复两篇事故）。
3. **场景A只回三字**：用户明确要求白天碎片只回"已记录"三字，不总结、不解释、不引用（2026.08.03 确立）。
4. **不漏天数**：遇到中间无消息跨 06:00 导致某日未触发时，主动补整理该日（源于 7/26 用户质问）。
5. **白天不写记忆**：日记碎片不写 memory_md，只留存 qa 层，整理时从 qa 检索（2026.07.20 确立）。
6. **导出格式**：必须用 `format=1`（Markdown），`format=0`（纯文本）会丢光换行导致不可读。
7. **IMA 笔记 API 不支持删除**：重复笔记只能由用户在 IMA 客户端手动删除。
